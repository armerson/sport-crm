# ClubOS architecture

ClubOS is a React 19 + TypeScript + Vite single-page app (installable PWA) on
Supabase (Postgres with RLS, Auth, Storage, Edge Functions in Deno) and Stripe.
It is deployed on Vercel. Ambassadors FC is the flagship club.

Key decision: [ADR 0001 — club isolation model](docs/adr/0001-club-isolation-model.md).

## Products and where they live

| Product | Today | Direction |
| --- | --- | --- |
| ClubOS App (coaches, parents, players) | This repo, PWA | Same code, Capacitor iOS/Android ([MOBILE_APP_ROADMAP.md](MOBILE_APP_ROADMAP.md)) |
| ClubOS Admin | This repo, admin workspace | Same app, role-gated |
| ClubOS Websites | Separate Ambassadors website repo; `/club-website` starter here | Separate public renderer fed by a public read model ([WEBSITE_BUILDER_ROADMAP.md](WEBSITE_BUILDER_ROADMAP.md)) |
| ClubOS Media | Graphics Studio in the website repo; caption and Instagram functions here | Media module in this app, approval-gated publishing |
| Platform admin | Not built | Control-plane project, operator only (Phase 2) |

## Runtime modes

Set by `VITE_CLUBOS_MODE` at build time.

| Mode | Backend | Used for |
| --- | --- | --- |
| `standalone` (default) | `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` | One deployment per club, e.g. Ambassadors today |
| `directory` | None | Central "find your club" site linking to club deployments |
| `multi` | Chosen club's `backend` from the registry | One web/native app for many clubs |

## Source layout

```
src/clubos/
  registry.ts   Registry schema and strict validation (pure)
  session.ts    Mode, club selection, storage namespacing, entry links (pure)
  plans.ts      Subscription packages and feature entitlements (pure)
  runtime.ts    Browser wiring: loads registry, selects club, scoped storage
src/lib/supabase.ts   The only Supabase client; built from runtime.activeBackend
src/pages/ClubDirectoryPage.tsx   /clubs finder
src/pages/ClubEntryPage.tsx       /clubs/<code>/<entry> club links
src/services, hooks, components   Club features (unchanged by Phase 1)
supabase/migrations   Version-controlled schema for every club backend
supabase/functions    Edge Functions deployed to every club backend
supabase/tests        SQL permission tests (run in rollback-only transactions)
tests/                Node unit tests (npm test)
e2e/                  Playwright browser tests (npm run test:e2e)
```

Code that is pure (no `import.meta.env`, no `window`) lives in `registry.ts`,
`session.ts` and `plans.ts` so it can be unit-tested with `node --test`.

## Club registry schema

`VITE_CLUBOS_REGISTRY_JSON` is a JSON array. Each entry:

```jsonc
{
  "code": "ambassadors-fc",          // required, unique, [a-z0-9-], 2–40 chars
  "name": "Ambassadors FC",          // required
  "sport": "football",               // default football; any lowercase slug
  "status": "active",                // active | onboarding | suspended
  "location": { "town": "...", "region": "...", "country": "..." },
  "branding": { "primaryColor": "#17466e", "secondaryColor": "#ffffff", "badgeUrl": "https://..." },
  "origin": "https://crm.club.example",   // its own deployment, if any
  "website": "https://club.example",
  "backend": { "supabaseUrl": "https://<ref>.supabase.co", "anonKey": "<anon JWT or sb_publishable_ key>" },
  "plan": "club",                     // id from plans.ts
  "features": { "mediaStudio": true } // operator overrides
}
```

A club needs `origin`, `backend` or both. Only `active` clubs are shown or
selectable. The whole registry is rejected if any entry is invalid.

## Club links

- `/clubs` — finder (search by name, code or town; "Continue" to last club).
- `/clubs/<code>` → sign in; `/clubs/<code>/register`, `/register/parent`,
  `/register/<form>`, `/join/<invite>`, `/join/club/<invite>`, `/pay/camp/<id>`,
  `/reset-password`. Any other path is refused.
- In multi mode, invitation, registration, camp-payment, email-confirmation and
  password-reset links generated by the app include `/clubs/<code>`, so they open
  the right club on any device. In standalone mode links are unchanged.

## Browser state

In multi mode, the auth token (`clubos:club:<code>:auth`), profile cache, club
settings cache and pending invite codes are namespaced per club. Standalone
deployments keep their original keys, so existing sessions are not signed out.
Remaining unscoped UI preferences (banner dismissals, message drafts, unread
markers, selected team) are listed in [MULTI_CLUB_ROADMAP.md](MULTI_CLUB_ROADMAP.md).

## Environments

- Local: `supabase start` (Docker) and `.env.local` pointing at
  `http://127.0.0.1:54321`. `.env.example` no longer points at a live club.
- Preview: Vercel preview with a separate staging backend. A preview using
  production data is not an isolated test environment.
- Production: one Vercel project and one Supabase project per club in
  standalone mode.

## Verification

`npm run lint`, `npm test`, `npm run build`, `npm run test:e2e` (CI:
`.github/workflows/verify.yml`). SQL permission tests in `supabase/tests` run
against a local stack or inside rollback-only transactions.
